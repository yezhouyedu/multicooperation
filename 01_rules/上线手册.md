## 2. 生产结构

```text
Browser
  -> nginx :80/:443
       -> /      -> web:3000
       -> /api/* -> server:3001
  -> PostgreSQL volume
  -> server storage volume
```

四类服务：

- `postgres`：结构化实验数据。
- `server`：实验运行时、AI、记录、导出和 Admin API。
- `web`：参与者流程和 Admin 前端。
- `nginx`：HTTPS、域名跳转和 `/api/*` 反向代理。

生产目录与数据：

- 代码：`/opt/multi-cooperation`
- 真实环境变量：`/opt/multi-cooperation/.env.production`
- 证书：`/etc/multi-cooperation/certs`
- PostgreSQL：Docker volume `multi-cooperation_postgres_data`
- 材料运行时副本、AI 图片、导出包：Docker volume `multi-cooperation_server_storage`，容器内 `/app/storage`
- Admin 扫描源材料：`/opt/multi-cooperation/00_start_materials/原始材料`

## 3. 当前部署路线

业务代码只在本地仓库修改。完成本地构建、commit 和 push 后，优先从本地上传当前 git HEAD：

```powershell
cd "E:\Own_program\multi cooperation"
powershell -ExecutionPolicy Bypass -File scripts/deploy/upload-git-archive.ps1 -Service all -AllowDirty
```

按影响面选择：

- `-Service web`：纯前端页面、样式或文案。
- `-Service server`：后端、导出、实验流程或 migration。
- `-Service all`：前后端都有修改或影响面不确定。

服务器直连 GitHub 只作备用；遇到 GitHub 443 超时或私仓凭据错误时，不要反复重试。

## 4. 正式实验前验收顺序

1. 本地执行 server/web build 和相关测试。
2. 部署前备份 PostgreSQL 与 `server_storage`。
3. 部署当前已提交 git HEAD。
4. 检查四类容器、migration 和 `/api/health`。
5. 用两名测试被试完成三段全流程。
6. 从 Admin 导出 zip，并按 `数据库文件夹手册.md` 审查。
7. 完成一次从备份恢复的演练。
8. 确认 HTTPS 全链路后关闭公网 3000/3001。

## 5. 安全边界

- 不把 SSH/证书私钥内容、生产密码或 AI key 写入仓库和 Markdown。仓库外私钥的本机路径可以只在运维命令文档中记录，便于执行，但路径本身不代表密钥内容。
- 不执行 `docker compose down -v`。
- 不执行 `docker volume rm multi-cooperation_postgres_data`。
- 不执行 `docker volume rm multi-cooperation_server_storage`。
- 不手动删除 `/var/lib/docker/volumes/...` 下的生产数据。
- Admin 密码只由服务器 `ADMIN_PASSWORD` 提供。
- migration、材料导入和实验数据清理前必须先备份。
